# STEP 22C — Case Results Response ID

## Schema

Case Results now uses columns `A:N`. Existing columns `A:M` are unchanged; `N` is the trailing `Response ID` column.

## Identity and deduplication

Every new Case Results row stores the deterministic Response ID already generated by the Form-response processor. Case Results deduplication reads only column `N`: an exact existing Response ID prevents another append. Identical Form field values with different Response IDs remain separate submissions.

## Legacy rows

Existing historical rows retain their existing values. A blank `Response ID` is a legacy row and never suppresses a new submission. No historical ID is inferred or populated by this change.

## Ambiguous append recovery

The writer checks column `N` before an append. If a transient append error occurs, the existing retry path repeats the read-check-append sequence. If the ID is found after an uncertain result, the write is treated as complete and no duplicate row is appended.

## Local writer lock

The read-check-append sequence holds a non-blocking Windows local file lock. A second local process fails safely while the lock is held, and the lock releases through `finally` on success or exception. This is single-host protection only; it is not a distributed transaction or multi-machine lock.

## Ledger relationship

- Case Results `Response ID`: durable evidence that a Case Results row exists.
- `.internal_notified_response_ids.json`: internal notification was confirmed and recorded.
- `.form_processed_response_ids.json`: the entire required workflow completed.

These states may temporarily differ after a crash. This change does not implement Gmail send reconciliation.

## Local test results

The fake-data test covers duplicate IDs, identical fields with different IDs, legacy blank IDs, timeout-after-write reconciliation, timeout-before-write retry, post-append crash recovery, and lock release/concurrency behavior. It does not contact Google or Gmail.
